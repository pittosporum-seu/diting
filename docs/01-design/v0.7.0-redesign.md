## 2. 架构问题诊断

按 v0.7.0-goals.md 的 5 个改进方向逐个诊断：

### 2.1 数据时效性问题

**问题：用户不知道"这数据是什么时候的"。**

| 现状 | 问题 | 影响 |
|:-----|:-----|:-----|
| API 响应无 `server_time` | 前端只能用 localStorage 写时间戳 | 不可靠：用户改系统时间、跨设备等 |
| `_dataTimeBar()` 用 `cacheManager.getEntry(key).ts` | 这是前端缓存写入时间，不是数据获取时间 | 偏差可达 5min（TTL 窗口内一直显示旧时间） |
| 缓存过期无提示 | TTL 到期后静默展示旧数据直到刷新成功 | 用户看到的是 10 分钟前的数据但以为是最新的 |
| MarketState 信息不暴露给前端 | 前端不知道现在是不是交易时段 | 盘后显示的数据无法标注"已收盘" |

**结论：需要服务端作为数据时间戳的唯一权威来源，每个 API 响应必须带 `server_time`。**

### 2.2 缓存策略问题

**问题：固定 5 分钟 TTL 不区分市场状态。**

当前缓存设计：

```
L1 内存 TTLCache: TTL=300s (全部 7 个实例统一)
L2 SQLite: 无 TTL，靠 updated_at + expires_at 手动管理
前端 localStorage: TTL=5min, STALE_MAX_AGE=30min
PrefetchWorker: 300s 间隔，仅 TRADING 运行
```

| MarketState | 当前 TTL | 合理 TTL | 差异 |
|:------------|:--------:|:--------:|:-----|
| TRADING (9:30-11:30, 13:00-15:00) | 300s | 30-60s | ❌ 太慢，盘中价格每秒在变 |
| CLOSED (盘后/午休) | 300s | 到下次开盘 | ❌ 太频繁，数据不变，浪费资源 |
| WEEKEND (周末/假期) | 300s | 到下次开盘 | ❌ 同 CLOSED |

另外：PrefetchWorker 只在 TRADING 时刷新 4 个端点（dashboard/watchlist/opportunities/sentiment），但 `analyze_stock`（个股分析）不在预刷新列表中。用户点个股时如果 TTL 到期，会在 TRADING 期间调 API。CLOSED/WEEKEND 时不调 API，返回兜底数据。

**结论：需要 MarketState 感知的 TTL 策略。**

### 2.3 错误处理问题

**问题：后台刷新失败时静默保持旧数据，用户不知道。**

| 场景 | 当前行为 | 问题 |
|:-----|:---------|:-----|
| Prefetch 刷新失败 | catch 异常 → 记日志 → 跳过 | ✅ 正确（不阻塞其他数据） |
| API 失败 + L2 有数据 | 返回 L2 旧数据 | ⚠️ 用户不知道数据可能过期 |
| API 失败 + 无缓存 | 返回空 dict / error dict | ⚠️ 前端显示"数据加载失败"但无错误上下文 |
| 个股分析 pipeline 异常 | catch → consensus=None → quick_score 兜底 | ⚠️ 引擎错误被静默吞掉，用户看到 50 分 |
| 前端 API 失败 + 有缓存 | 继续显示缓存数据 | ⚠️ 无"数据可能陈旧"的视觉提示 |

**结论：需要在响应中增加 `stale` 标志 + 前端显示轻量提示。**

### 2.4 前后端协作问题

**问题：缓存逻辑有重叠，没有清晰的数据主权划分。**

| 数据 | 后端缓存 | 前端缓存 | 冲突 |
|:-----|:--------:|:--------:|:-----|
| 实时行情 | L1 300s + L2 SQLite | localStorage 300s (SWR) | 双写，可能不一致 |
| 个股分析 | L1 300s + L2 SQLite | localStorage 300s (SWR) | 同上 |
| 仪表盘 | L1 300s + L2 SQLite | localStorage 300s (SWR) | 同上 |
| 时间戳 | 无 | 客户端写入时间 | 无权威源 |

**设计原则（v0.7.0 确立）：**

1. **后端是数据的唯一权威来源**（Single Source of Truth）
2. **后端提供 `server_time`**：数据实际获取/计算的时间
3. **后端提供 `cache_state`**：fresh（直接来自 API）/ stale（来自缓存）/ empty（无数据）
4. **前端 localStorage 只做展示加速，不做数据权威判断**
5. **前端用 `server_time` 显示时间，不用自己写的时间戳**
6. **TLL 由后端统一管理**：通过 `Cache-Control` 头或响应字段告知前端

### 2.5 代码组织问题

| 问题 | 现状 | 影响 |
|:-----|:-----|:-----|
| services.py 过大 | 1385 行，混合路由桥接 + 缓存逻辑 + 数据分析 | 改一处可能影响多处 |
| 两份 TTLCache | `web/cache.py` 和 `cache/cache_manager.py` 各有一个 | 维护负担、行为不一致 |
| 缓存实例散布 | 7 个模块级 TTLCache 在 `web/cache.py` | 无法统一管理 TTL |
| 前端单文件 | app.js 1560 行 | 功能耦合、难以测试 |
| routes.py 弱 | 只做请求/响应转换 | ✅ 职责清晰 |

**分层评分：**

```
routes.py    ✅ 职责清晰 — 只做请求/响应转换
services.py  ⚠️ 过重 — 缓存+数据+分析+编排混在一起
cache.py     ⚠️ TTL 硬编码 — 不感知 MarketState
cache/       ✅ 结构清晰 — market_state + prefetch + cache_manager
app.js       ⚠️ 单体 — 路由+渲染+缓存+UI 混在一起
api.js       ✅ 职责清晰 — 只做网络请求
```

## 3. 新架构设计

### 3.1 核心变化

```
                    v0.6.x                           v0.7.0
─────────────────────────────────────────────────────────────────
数据时间源    │ 前端 localStorage ts       │ 后端 server_time (权威)
缓存 TTL     │ 固定 300s                  │ MarketState 分层
错误可见性   │ 静默失败                    │ stale 标志 + 轻量提示
缓存主权     │ 前端 SWR + 后端 TTLCache   │ 后端统一控制，前端只展示
时间戳展示   │ 前端写入时间               │ 服务端时间（ISO 8601）
```

### 3.2 新数据流

```
用户打开页面
  │
  ▼
前端: _loadWithCache(cacheKey, skeletonFn, apiFn, renderFn)
  │
  ├── Phase 1: localStorage 缓存命中？
  │   ├── YES → 立即渲染缓存数据（0ms），标注 "数据加载中…"
  │   └── NO  → 显示骨架屏
  │
  ├── Phase 2: 调 API
  │   └── GET /api/{endpoint}
  │       │
  │       ▼
  │   后端: AnalysisService.get_*()
  │       │
  │       ├── force_refresh? → 跳过缓存，直接调 API
  │       │
  │       ├── L1 内存 TTLCache (MarketState-aware TTL)
  │       │   ├── HIT → 返回 { data, server_time, cache_state: "fresh" }
  │       │   └── MISS → 查 L2
  │       │
  │       ├── L2 SQLite
  │       │   ├── HIT → 补回 L1，返回 { data, server_time, cache_state: "stale" }
  │       │   └── MISS → 调 API
  │       │
  │       └── MarketState 守卫
  │           ├── TRADING → 调 API
  │           ├── CLOSED  → 不调 API，返回 L2 数据 (或空)
  │           └── WEEKEND → 不调 API，返回 L2 数据 (或空)
  │
  ├── Phase 3: API 返回
  │   ├── OK + cache_state="fresh" → 更新 localStorage + server_time + 绿色时间戳
  │   ├── OK + cache_state="stale" → 更新 localStorage + 显示 "数据可能滞后" 黄色
  │   └── ERR + localStorage 有缓存 → 保留缓存 + 显示 "刷新失败" 灰色提示
  │
  └── Phase 4: 渲染
      └── 时间戳栏: 📡 数据时间 {server_time} [● fresh / ◉ stale / ○ cached]
```

### 3.3 架构分层（v0.7.0）

```
┌─────────────────────────────────────────────────────────────────┐
│  Layer 5: Presentation (前端 SPA)                                │
│  ├─ cacheManager: localStorage 只缓存展示数据 (不做时效判断)      │
│  ├─ _dataTimeBar(): 使用 server_time 显示                         │
│  └─ 新鲜度指示器: ● fresh (绿色) / ◉ stale (黄色) / ○ cached (灰)│
├─────────────────────────────────────────────────────────────────┤
│  Layer 5b: API Gateway (routes.py)                               │
│  ├─ 所有端点统一包装: { data, server_time, cache_state, error }  │
│  └─ 中间件: 统一注入 server_time                                  │
├─────────────────────────────────────────────────────────────────┤
│  Layer 4: Services (services.py → 拆分)                          │
│  ├─ StockService: 个股相关 (analyze, realtime, historical)        │
│  ├─ DashboardService: 仪表盘相关                                  │
│  ├─ WatchlistService: 自选股 CRUD                                 │
│  ├─ ScanService: 选股扫描                                         │
│  └─ SettingsService: 设置管理                                     │
├─────────────────────────────────────────────────────────────────┤
│  Layer 3: Cache (统一缓存管理)                                    │
│  ├─ MarketState: 市场状态判断                                     │
│  ├─ CacheManager: L1(内存) + L2(SQLite) + TTL策略                │
│  ├─ PrefetchWorker: 后台预刷新 (MarketState-aware)                │
│  └─ CachePolicy: TTL 策略矩阵 (按数据类×MarketState)              │
├─────────────────────────────────────────────────────────────────┤
│  Layer 1-2: Data + Analysis (不变)                                │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 server_time 时间戳流

```
数据获取时间点:
  API 调用成功 ──→ datetime.now() ──→ 写入 RealtimeQuote.timestamp
  L1 缓存写入   ──→ time.time()    ──→ TTLCache._data[key] = (ts, value)
  L2 SQLite 写入──→ datetime.now() ──→ updated_at 列
  返回响应      ──→ datetime.now() ──→ server_time (ISO 8601)

前端接收:
  server_time ──→ _dataTimeBar() 显示 ──→ "📡 数据更新于 07-13 14:35:22"
  cache_state  ──→ 新鲜度指示器颜色
    "fresh" ──→ 🟢 绿色圆点 "最新数据"
    "stale" ──→ 🟡 黄色圆点 "数据可能滞后"
    "cached"──→ ⚪ 灰色圆点 "已缓存数据"
```

## 6. 前端渲染逻辑

### 6.1 统一加载流程

```

                          │
                    ┌─────▼────┐
                    │localStorage│

                    └──┬────┬──┘
                   YES │    │ NO
                       │    │
              ┌────────▼┐ ┌─▼──────┐

                   │          │
                   └────┬─────┘
                        │
                  ┌─────▼─────┐

           │cache_state│ │localStorage │
           │ = fresh?  │ │  有缓存？    │
           └──┬─────┬──┘ └──┬──────┬──┘
        YES   │     │ NO  YES│      │NO
              │     │       │      │

    │渲染新数据│ │渲染数据│ │保留 │ │显示错误│

    └─────────┘ └───────┘ └─────┘ └───────┘
```

## 7. 缓存策略矩阵

### 7.1 TTL 策略（MarketState-aware）

| 数据 | TRADING TTL | CLOSED TTL | WEEKEND TTL | 说明 |
|:-----|:----------:|:----------:|:----------:|:-----|
| 实时行情 | 30s | 到下次开盘 | 到下次开盘 | 盘中价格变化快 |
| 个股分析 | 60s | 到下次开盘 | 到下次开盘 | 含技术指标+AI评分 |
| 仪表盘 | 60s | 到下次开盘 | 到下次开盘 | 大盘指数+信号 |
| 自选股列表 | 30s | 到下次开盘 | 到下次开盘 | 价格依赖 |
| 选股机会 | 120s | 到下次开盘 | 到下次开盘 | 扫描耗时，降低频率 |
| 市场情绪 | 300s | 到下次开盘 | 到下次开盘 | 变化慢 |
| 历史K线 | 600s | 到收盘 | 到收盘 | 变化最慢 |
| 全市场扫描 | 3600s | 不刷新 | 不刷新 | 已在v0.6.5中使用 |

**"到下次开盘"的计算**：从 `MarketState.next_trade_date` + `time(9, 30)` 减去当前时间。

### 7.2 Prefetch 行为矩阵

| MarketState | Prefetch间隔 | 刷新端点 | 说明 |
|:------------|:----------:|:---------|:-----|
| TRADING | 30s | dashboard, watchlist | 盘中高频 |
| TRADING | 120s | opportunities, sentiment | 盘中中频 |
| CLOSED | — | 不刷新 | 市场没开 |
| WEEKEND | — | 不刷新 | 非交易日 |

### 7.3 错误回退矩阵

| 场景 | L1 | L2 | API | 行为 |
|:-----|:--:|:--:|:---:|:-----|
| 正常·TRADING·全热 | HIT | — | — | 返回 fresh |
| TRADING·L1过期·L2有 | MISS | HIT | 后台调 | 先返回 stale → 后台刷新 |
| TRADING·全冷 | MISS | MISS | 调用 | 调API → 返回 fresh |
| TRADING·API失败·L2有 | MISS | HIT | FAIL | 返回 stale + error_flag |
| TRADING·API失败·全冷 | MISS | MISS | FAIL | 返回 error |
| CLOSED·有缓存 | HIT/MISS | HIT | — | 返回 fresh/stale（不调API） |
| CLOSED·无缓存 | MISS | MISS | — | 返回 empty |
| WEEKEND·有缓存 | HIT/MISS | HIT | — | 返回 fresh/stale（不调API） |
| WEEKEND·无缓存 | MISS | MISS | — | 返回 empty |
