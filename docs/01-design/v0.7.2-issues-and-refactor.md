# 谛听 v0.7.2 系统问题梳理与重构方案

> 时间：2026-07-17  
> 状态：前端模块加载链已修，但渲染与后端数据新鲜度有多重问题

---

## 一、已修复问题（保留）

### 1.1 前端循环依赖 ✅

**问题：** `app.js → router.js → pages/stock.js → app.js` 循环 → 模块加载死锁  
**修复：** 创建 `core.js`（共享状态 + 工具函数），所有页面和路由从 `core.js` 单向引用。`disposePage`、`search` 函数也迁入 `core.js`。

**当前架构：**
```
core.js ←── cache.js, api.js, ui.js  (无业务依赖)
          ←── all pages              (单向引用)
          ←── router.js              (单向引用)
          ←── app.js                 (单向引用)
app.js  → core.js, router.js         (router.js 不反弹)
```

### 1.2 模块重复加载 ✅

**问题：** HTML 中 `?v=0.7.2` 与 `import ./core.js` 走不同 URL → 浏览器当两个模块 → core 加载两次  
**修复：** 删除所有 `?v=` 参数，由 Caddy `Cache-Control: no-cache` 处理缓存。

### 1.3 DOMContentLoaded 竞态 ✅

**问题：** HTML 太小，DOMContentLoaded 在模块加载前触发  
**修复：** `app.js` 使用 `document.readyState` 判断。

## 二、待修复问题（按优先级）

### P0: 后端数据新鲜度系统失效

**症状：**
- `force_refresh=true` 仍返回 `cache_state: stale`
- `freshness` 字段返回空 `{}`
- 上证指数数据停留在 `3996.16`，不刷新
- 页面显示"数据更新于 07-17 02:04:12 · 可能滞后"——但这是 server_time，不是数据时间

**根因分析：**
```
API 请求 → DashboardService.get_dashboard()
  → 检查缓存 (stale) → 返回旧数据
  → force_refresh=true → 尝试刷新 → 失败静默 → 返回旧数据
```

`freshness` 为空说明 `DashboardService` 没有正确传递 `_freshness` 元数据到响应中。数据源的刷新可能因网络/API 限流而失败，但错误被静默吞掉。

**重构方案：**

```
┌─ DashboardService ─────────────────────────────────────┐
│ 1. 分离 cache_layer 和 fetch_layer                     │
│ 2. fetch_layer 失败时返回具体错误（不静默降级到 stale）│
│ 3. freshness 在每一层显式传递：                         │
│    provider.fetch() → supply_freshness(timestamp)      │
│    → cache.set(data, fresh_until=...)                  │
│    → API response { freshness: {updated_at, source} }  │
│ 4. 前端根据 freshness 显示数据时间 + 来源               │
└────────────────────────────────────────────────────────┘
```

**数据新鲜度协议（schema 新增）：**
```python
@dataclass
class FreshnessInfo:
    updated_at: datetime        # 数据实际更新时间
    source: str                 # 数据来源 (mx-data / akshare / cache)
    ttl_seconds: int            # 有效期
    is_stale: bool              # 是否已过期
    refresh_error: str | None   # 刷新失败原因
```

### P1: stock_analysis_cache DB 字段解包错误

**症状：**
```
cache.db_get.failed  error='not enough values to unpack (expected 2, got 1)'
key=000001  table=stock_analysis_cache
```

**根因：** 某个版本中 `stock_analysis_cache` 表的列结构变了，但读取代码仍用旧的解包方式。`SELECT *` 或 `row = cur.fetchone()` 返回值列数与预期不符。

**修复：**
1. 检查 `stock_analysis_cache` 表实际结构：`PRAGMA table_info(stock_analysis_cache)`
2. 对齐读写两端的列数和顺序
3. 改用命名列访问（`row['key']` 而非 `row[0], row[1]`），防止列序漂移

### P2: 前端页面渲染函数批量失效

**症状：**
- 搜索 000001 后页面空白（0 字）
- 设置页面空白
- 选股机会页面空白
- 自选股数据极少

**根因：** 前端模块化拆分时，以下文件引入了 bug：
| 文件 | 问题 | 证据 |
|------|------|------|
| `stock.js` | 多一个 `}`，ES module parser 拒绝加载 | Node import test ✗ |
| `pages/opportunities.js` | render 逻辑返回空 | Playwright test: 内容为空 |
| `pages/settings.js` | 同上 | Playwright test: 内容为空 |
| `pages/watchlist.js` | render 不完整 | Playwright test: 仅标题 |

**重构方案：**
```
方案 A: 修复当前模块化文件（逐个修 bug）
  优点: 改动小
  缺点: 文件多，bug 散落，修完一个冒一个

方案 B: 重构为组件化架构 ─── 推荐！
  1. 公共渲染组件抽到 components/ 目录
  2. 每个页面只负责数据获取 + 组装组件
  3. 减少重复代码，降低 bug 面
```

**建议的文件结构：**
```
frontend/js/
├── core.js              # 状态 + 工具（已稳定）
├── api.js               # API 封装（已稳定）
├── cache.js             # 缓存（已稳定）
├── router.js            # 路由（已稳定）
├── app.js               # 入口（已稳定）
├── components/
│   ├── card.js          # 通用卡片
│   ├── indicator.js     # 指标展示
│   ├── chart.js         # 图表包装
│   ├── search-bar.js    # 搜索组件
│   ├── skeleton.js      # 骨架屏
│   └── score-bar.js     # 评分条
├── pages/
│   ├── dashboard.js     # 仪表盘（组合组件）
│   ├── stock.js         # 个股分析（重写）
│   ├── opportunities.js # 选股机会（重写）
│   ├── watchlist.js     # 自选股（重写）
│   └── settings.js      # 设置（重写）
```

**症状：**
- WSL 代理不稳定 → `git push` 频繁失败

```

  → 影响所有页面的数据可靠性

Phase 2: 修复 DB 解包错误（P1）
  → 解除股票数据获取阻塞

Phase 3: 重构前端页面（P2）

Phase 4: 加固部署流程（P3）

Phase 5: 添加 E2E 测试（P4）
```

## 四、技术决策记录

| 决策 | 原因 |
|------|------|
| 模块化保留，不退回单体 | 单体 58KB 不可维护，模块化是正确的架构方向 |
| 不引入构建工具（webpack/vite） | 项目规模不需要，ES modules 原生加载即可 |
| 前端组件化而非修 bug | 当前页面文件 bug 分散，逐个修不如重写为组件 |
| 后端 freshness 协议化 | 解决"数据是不是最新的"这个全栈问题 |
